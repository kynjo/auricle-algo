# Публикация Auricle на GitHub

Этот каталог — полный проект v2.0. Для публикации загрузите его содержимое в корень репозитория, включая `.github/`, `.gitignore` и `.gitattributes`. Временные окружения, кэши, журналы и результаты сборок в комплект не включены. Сохранённые проекты находятся в `projects/`, прежние отчёты и patch-манифесты — в `docs/history/`. При публикации проверьте, какие личные проекты следует включать в репозиторий. Результаты текущей проверки приведены в [отчёте об уборке](CLEANUP_RU.md).

## Перед первым релизом

1. Проверьте `README.md`, `CHANGELOG.md` и скриншот `docs/screenshots/auricle-v2.0.png`.
2. Если проекту нужна открытая лицензия, выберите её и добавьте `LICENSE`. Лицензия и сведения об авторе не были выдуманы при подготовке архива.
3. Убедитесь, что GitHub Actions разрешены. Выполните ручной запуск **Actions → Release → Run workflow**. Это соберёт приложения и сохранит их в Artifacts без публикации GitHub Release.
4. Скачайте сборку для своей системы и проверьте воспроизведение через свой MIDI-порт.

Первичная отправка в собственный пустой репозиторий (подставьте его URL):

```sh
git init
git add .
git commit -m "Prepare Auricle v2.0 release"
git branch -M main
git remote add origin <URL-вашего-репозитория>
git push -u origin main
```

## Выпуск v2.0

Тег должен совпадать с `APP_VERSION` из `version.py`; версия wheel задаётся там же в `PACKAGE_VERSION`. Заголовок `CHANGELOG.md` также проверяется автоматически.

```sh
git tag -a v2.0 -m "Auricle v2.0"
git push origin v2.0
```

После успешных тестов и четырёх сборок workflow опубликует Release с содержимым `CHANGELOG.md`, приложениями и `SHA256SUMS.txt`. Ссылки на скриншот и документацию в описании автоматически привязываются к коммиту сборки, поэтому не требуют заранее заданного имени аккаунта или репозитория. GitHub также предоставляет собственные source ZIP / tar.gz для тега.

Если тег `v2.0` уже существует, не перезаписывайте его: подготовьте новую версию в `version.py`, обновите заметки и имена в документации, создайте новый тег. Повторный запуск workflow существующего релиза может заменить его вложения.

## Проверка SHA-256

Linux: `sha256sum -c SHA256SUMS.txt` после скачивания всех указанных файлов. macOS: `shasum -a 256 <имя-файла>`. PowerShell: `Get-FileHash <имя-файла> -Algorithm SHA256`; сравните результат со строкой в `SHA256SUMS.txt`.

## Что настроено

| Workflow | Когда запускается | Результат |
| --- | --- | --- |
| CI | Push в ветку, pull request, вызов из Release | Тесты, wheel/sdist, проверка запуска wheel |
| Release | Ручной запуск | Четыре нативных файла в Artifacts |
| Release | Push тега `v*`, совпадающего с версией | Те же файлы и опубликованный GitHub Release |

GitHub Actions не выполнялись в процессе подготовки исходного архива; их фактический результат будет виден после запуска в вашем репозитории. Сценарии не содержат ключей подписи, токенов или адреса чужого репозитория. Для публикации используется штатный `GITHUB_TOKEN`.

# MIDI Learn: диагностика после сообщения «не помогло»

Эта версия не объявляет аппаратный сбой устранённым без данных с компьютера
пользователя. Предыдущий патч исправлял воспроизводимые программные дефекты,
но пользователь сообщил, что его случай остался нерешённым.

## Изменения

1. В MIDI IN видны отдельные счётчики сообщений, полученных от Mido до
   отбора пригодных для Learn типов, декодированных сообщений и сообщений,
   дошедших до обработчика Qt. Отдельно фиксируются Learn, ожидание Pickup,
   несовпадение привязки, постановка изменения в очередь и наблюдаемое
   изменение ручного значения параметра.
2. Кнопка **Copy diagnostics** копирует состояние этих этапов, последний
   тип сообщения и значения, выбранный/фактический вход, состояние потоков,
   очередь/ошибки команд, привязки и выбранную цель Learn.
3. В отчёте есть ОС, Python, версии библиотек, фактические пути загруженных
   GUI/reader-модулей, контрольная сумма GUI и метка
   `midi-learn-diagnostics-2`. Это позволяет проверить, какая копия
   программы действительно запущена.
4. Менеджер MIDI IN стал немодальным: он остаётся открытым, пока пользователь
   выбирает MIDI Learn у параметра в Inspector. Раньше диалог exec() блокировал
   доступ к основному окну до своего закрытия. Повторный вызов показывает
   существующий менеджер, а закрытие удаляет его и приёмники сигналов.
5. Новый диагностический модуль включён в pyproject.toml для сборки wheel.

## Что покажут наблюдения

| Наблюдение | Вывод, который действительно можно сделать |
| --- | --- |
| Reader работает, Received = 0 | Открытый Mido-вход пока не возвращает сообщений. Это не доказывает, что неисправен сам контроллер. |
| Received > 0, Supported = 0 | Mido возвращает сообщения, но они не относятся к поддержанным управляющим типам. Последний тип указан в отчёте. |
| Supported > 0, GUI = 0 | Сообщение декодировано reader-потоком, но не зарегистрировано обработчиком Qt. |
| Stage = unmatched | Не совпадают порт, канал, тип/номер сообщения либо привязка отключена/отсутствует. |
| Stage = pickup | Привязка совпала, но контроллер ещё не подхватил ручное значение параметра. |
| Stage = queued | Изменение направлено в очередь. Состояние TransportWorker, длина очереди и текущее значение помогают проверить применение. |
| Stage = applied | Запрошенное ручное значение наблюдается в модели. Эффективное значение может отличаться из-за автоматических слоёв; оба значения отражены в деталях. |

Счётчик Received относится к объектам сообщений, возвращённым Mido, а не к
сырым USB-пакетам. Диагностика ничего не посылает в Интернет. Полное окружение
процесса не собирается, поток сообщений не сохраняется без ограничений,
содержимое System Exclusive не копируется: только тип и длина.

## Проверки

Сохранены 38 профильных проверок из предыдущего патча и добавлены 8 новых.
Все 46 проверок пройдены. Компиляция изменённых модулей успешна; wheel
собирается и содержит все новые диагностические зависимости.
Дополнительные проверки используют настоящий класс `mido.backends.rtmidi.Input`,
его обработчик байтов, ParserQueue, polling, queued signals Qt и работающий
TransportWorker. Тест не вызывает ручной flush очереди ради получения
ожидаемого результата. Только устройство/OS-граница MidiIn заменена тестовым
объектом, который отправляет MIDI-байты из отдельного потока.

Проверены CC → Learn → изменение параметра обычным worker, несовпадающее
сообщение, ожидание Pickup, неподдержанный clock, скрытие содержимого SysEx,
диагностика неработающего worker, немодальное окно с обучением и удалением
после закрытия, копирование отчёта и параллельное наблюдение сообщений.

Физическое устройство пользователя недоступно. Для установления причины
именно его сбоя нужен отчёт Copy diagnostics, снятый после движения ручки
или нажатия клавиши при открытом выбранном входе.

Полный набор тестов приложения повторно в этой итерации не запускался.
Предыдущий сравнительный прогон обнаружил одинаковые 131 исходный сбой в
исходной версии и в первом патче; эти сбои данной диагностикой не закрываются.
